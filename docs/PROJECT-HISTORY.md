# How we built Chroma Likeness for Marinara Engine

Project history and design notes · Version 3.1.2 · November 20, 2026

Chroma Likeness grew out of a specific failure. A hearted selfie showed a character with an ash-brown wolf cut and a round face. In the next exchange, the chat model described her with dark-blonde hair, freckles and a septum ring. The image generator had been given a different person to draw. The user wanted the same woman in a new moment, with the freedom to change her clothes, pose, accessories or surroundings.

That example shaped the extension. A heart chooses **who someone looks like**. The conversation supplies **what is happening now**. For follow-up photos, an image editor receives the approved picture itself alongside the scene instructions. This document describes how we arrived at that design, what each control means, and where the current implementation stops.

## From a companion program to an extension

Earlier work on Handy Adaptive had introduced the idea of pictures arriving in character chat. Likeness needed to work whenever Marinara was open, including sessions with Handy Adaptive disabled. We gave it its own package and controls.

The first prototype ran a local Node.js service with a separate browser gallery. Marinara sent it an avatar, sprite or character sheet. The service recognized the exact bytes of that file and associated a hearted picture with it. This proved the generation-to-edit workflow, but changing the avatar started a new history, and two cards using the same asset could share a selection. Using it also meant running a second program and switching windows to choose a reference.

The user asked for an importable ZIP like Handy Adaptive, with setup and testing inside Marinara. The current package contains a manifest, a client script and a stylesheet. Its Likeness panel handles provider settings, tests, character selection, generation and feedback. It uploads a finished image to Marinara’s gallery and attaches it to a chat message. The extension keeps the submitted prompt in attachment metadata for inspection. Scene drafting also strips recognized inline selfie tags so their instructions do not keep feeding into later drafts. Other agents still control the text they put in their own replies.

Status lines and notices aren't repeated for network errors. **SpicyAPI jobs:** a failed status check (network, 5xx, 429) is logged once and retried every 5 seconds until the job's timeout; the download retries up to 4 times (alternating with the relay if one is set). **Writing model:** one retry after 4 seconds when unreachable. **Late pictures:** no longer kept out of the chat. They're posted under the reply they were made for: `deliver()` and `postMedia()` take `forMessage`, and `attachToLatest()` attaches to that message. Her Conversation text is left off a late photo. **Wardrobe:** `wardrobeAdd` is only applied when the user's message (or the reply) mentions the wardrobe or closet, or the user says save, keep, add, store or remember about an outfit; otherwise it's skipped with a log line. Test: `test_continuity.py` step 9 (a dropped status check plus a newer reply; the picture attaches to its own reply). |

## What a heart and a rating actually do

**Heart a solo portrait.** The extension saves the image for the selected person and asks a Venice vision model to describe six visible features — face, eyes, nose, hair, skin and build. Its instructions exclude clothing, pose, lighting and setting, and ask it to leave uncertain features blank. The user can correct the resulting appearance notes. This matters when a warm bulb makes brown hair look blonde or the reference crops out most of the body.

**Rate a follow-up.** A thumbs-up asks the vision model which features most clearly match the approved reference. A thumbs-down asks which visibly differ. It can select up to three. Matching features receive one point of emphasis and mismatches receive two. Later edit prompts emphasize up to three of the highest-scoring features from the reference. Clicking the same rating again removes the vote. For example, a downvote on a blonde follow-up can increase attention to the approved brown hair if the comparison identifies hair as the discrepancy.

This is how “learning” works in this release. The extension accumulates evidence about which details to emphasize in future requests. The provider model’s weights stay fixed, and visual consistency still depends on the reference, the comparison and the editor. The main character and each saved friend have separate profiles, so feedback on one person can be kept with that person.

## How pictures enter a conversation

**Manual generation.** Choose a character or friend and optionally a second person under *Also pictured*. Type a scene or use *Draft from recent chat*. The draft considers up to six recent messages and the last saved scene for that chat and combination of people. A new location or change of outfit in the dialogue takes precedence. The user can review the draft before generating. A solo subject can start without a heart. A paired render needs a solo heart for both people.

**Contextual photos.** Once enabled for a chat, the extension checks new assistant replies while Marinara is open. Its writing model receives the roster of saved people, recent turns and available picture metadata. Consider a character called Alex and her saved friend Jo. “Jo sent me this selfie” should picture Jo alone, even though Alex sent the message. “Show me both of you at the café” should use Alex’s and Jo’s references together. “Jo might visit next week” should produce no picture. These are intended decisions. *Preview who would be pictured* lets the user inspect the model’s interpretation on a real exchange.

The planner handles one or two known people and is instructed to skip ambiguous subjects and larger groups. It records the processed reply to avoid repeat charges for that turn. If the conversation moves on during rendering, the result can remain in the gallery without posting a stale photo into chat.

**Built-in selfies and Illustrator.** The panel can apply portrait settings to a selected chat and point Marinara’s native image tools at a matching image connection. A separate follow-up mode watches for eligible new native pictures of one identified, hearted character and posts an additional reference edit. This differs from contextual photos, which can initiate a picture from dialogue alone. The extension watches one chat in one of these modes at a time.

## Providers, persistence and verification

| Responsibility | Where it lives in 1.7.0 |
| --- | --- |
| Character dialogue | The chat connection selected in Marinara. It can use NanoGPT independently of the extension. |
| Scene drafting and cast decisions | The writing model selected in Likeness, on NanoGPT or SpicyAPI. Contextual mode can incur a text call on each eligible new reply, even when it chooses no photo. |
| Describing hearts and comparing rated photos | The vision model selected in Likeness, on NanoGPT or SpicyAPI, if any. Each new description or comparison sends the relevant image or images to that provider. Without one, hearts save without automatic notes and ratings record only up or down. |
| Rendering extension pictures | The SpicyAPI generation and editing models selected in Likeness, built from each model's input schema. Reference pictures are uploaded to SpicyAPI storage for about a day. |
| Portable character information | The character card contains the saved reference, appearance notes, ratings and nested friend profiles, and, when sharing is on, the Image appearance. Browser settings hold the keys, monitoring state and recent scene history. |

Development checks covered the packaged ZIP, native card export round trips, reference ordering for paired photos, cast routing, duplicate handling and provider-specific request construction. The user reported receiving rendered photos during development. The 1.7.0 NanoGPT checks used simulated responses, so they establish how the extension builds and routes requests. The 1.8.0 changes were exercised in headless Chrome against mocked Marinara and NanoGPT endpoints. A real SpicyAPI key has not yet been used. Marinara stores connection keys server-side and does not expose them to extensions, so Likeness still needs its own copy of the key.

The original brown-hair example is also a useful acceptance test. Heart a clear solo photo, ask for the same person outdoors in a different outfit, and inspect the face and haircut as well as the new scene. Then ask for a friend alone, followed by both people together. That sequence tests the three things the project set out to preserve in everyday chat — a recognizable person, a scene that can change, and the right people in the frame.
